🔥 Kotlin Coroutines – Advanced Scenario-Based Interview Q&A

Master real interview questions: from cancellation to dispatcher internals, structured concurrency, Flow, testing, and anti-patterns. Includes original scenarios + 10+ new advanced scenarios with expert explanations.

📌 Core Scenarios (Must-Know)

#1 Network call Scenario: Background thread network call & UI update 
suspend fun fetchUser(): String { delay(2000); return "User Data" }
fun main() = runBlocking {
    withContext(Dispatchers.IO) {
        val result = fetchUser()
        withContext(Dispatchers.Main) { println(result) }
    }
}
✅ Interview answer: withContext(Dispatchers.IO) moves work off main thread without blocking. withContext(Dispatchers.Main) switches back to UI. This is the preferred approach over launch + async for simple thread switching.
#2 Parallel API Scenario: Parallel API calls (async/await) 
suspend fun getProfile() = delay(1000).let { "Profile" }
suspend fun getPosts() = delay(1500).let { "Posts" }
fun main() = runBlocking {
    val profile = async { getProfile() }
    val posts = async { getPosts() }
    println("${profile.await()} + ${posts.await()}")
}
💡 Key insight: Both requests run concurrently, total time ~1.5s (not 2.5s). async starts immediately, await suspends until result ready. Perfect for independent tasks.
#3 Cancellation Scenario: Cancel long-running task 
val job = launch {
    repeat(10) { delay(500); println("Downloading $it") }
}
delay(2000); job.cancel(); println("Download cancelled")
⚡ Explanation: delay() is cancellable; after cancellation, remaining iterations won't run. Always use cancellable suspend functions or check isActive for heavy loops.
#4 Exception Handler Scenario: Global exception handling 
val handler = CoroutineExceptionHandler { _, ex -> println("Caught: ${ex.message}") }
launch(handler) { throw RuntimeException("Something went wrong") }
⚠️ Note: CoroutineExceptionHandler only works for root coroutines (launch). Does NOT catch exceptions inside async — those are thrown in await().
#5 Structured concurrency Scenario: Parent-child cancellation 
val parent = launch {
    launch { delay(1000); println("Child 1") }
    launch { delay(2000); println("Child 2") }
}
delay(500); parent.cancel() // both children cancelled
🏛️ Structured concurrency = parent waits for children, cancellation propagates downward. No orphan coroutines!
#6 Thread switching Scenario: CPU work → UI 
withContext(Dispatchers.Default) {
    val result = (1..1_000_000).sum()
    withContext(Dispatchers.Main) { println("Result: $result") }
}
🎯 Dispatchers.Default is optimized for CPU tasks (limited threads = core count). Never do heavy computation on Main or IO.
#7 Timeout Scenario: Timeout handling 
val result = withTimeoutOrNull(3000) { delay(5000); "Success" }
println(result ?: "Timeout occurred")
⏱️ withTimeoutOrNull returns null on timeout (no exception). Use withTimeout when you need to throw TimeoutCancellationException.
#8 Flow Scenario: Cold stream with backpressure 
fun numberFlow() = flow { repeat(5) { emit(it); delay(1000) } }
fun main() = runBlocking { numberFlow().collect { println(it) } }
🌊 Flow is cold: each collector triggers the producer. Use operators like flowOn, catch, buffer for production.
#9 ViewModelScope Scenario: Lifecycle-aware coroutine (Android) 
viewModelScope.launch { delay(2000); println("Data loaded safely") }
📱 Automatically cancels when ViewModel cleared → prevents leaks. Always use instead of GlobalScope for UI-bound work.
#10 Lightweight Scenario: 10k coroutines vs threads 
repeat(10_000) { launch { delay(1000); print(".") } }
🚀 Coroutines use ~KB memory vs MB per thread. This runs smoothly; threads would crash.

🔐 Advanced + Tricky Interview Scenarios (New)

🔥 #11 supervisorScope vs coroutineScope Scenario: Independent failure handling 
supervisorScope {
    launch { throw RuntimeException("Task A fails") }
    launch { delay(500); println("Task B still runs!") }
}
// coroutineScope would cancel B immediately.
🎙️ Answer: supervisorScope isolates failure. Perfect for loading multiple UI widgets where one failure shouldn't crash the whole screen. Used heavily in Android.
🧠 #12 Cancellation is cooperative — Why is my coroutine still running? 
val job = launch {
    while (true) {
        // heavy calculation — no suspension, no isActive check
    }
}
job.cancel() // DOES NOTHING 😱
✅ Fix: add yield() or ensureActive() or if (!isActive) break. Cancellation only works at suspension points or explicit checks.
💡 Interview hack: Mention job.cancelAndJoin() to wait for actual cancellation completion.
⚠️ #13 Async exception swallowing Scenario: Silent failure using async without await 
val deferred = async { throw IllegalStateException("Crash") }
// no await() → exception never observed! (potential bug)
🔥 Answer: Exceptions in async are only thrown when you call await(). Always attach a parent or use coroutineScope to propagate.
🔄 #14 Dispatcher inheritance — tricky behavior 
runBlocking(Dispatchers.IO) {
    launch {
        println(Thread.currentThread().name) // still IO? Yes, inherits from parent
    }
    withContext(Dispatchers.Default) {
        launch { // inherits Default now
            println(Thread.currentThread().name) // DefaultDispatcher
        }
    }
}
📌 Child coroutines inherit parent's context (including dispatcher) unless overridden. withContext does NOT change the parent context for new launches inside it.
⛔ #15 GlobalScope is evil — leak scenario 
class MyActivity : AppCompatActivity() {
    fun loadData() {
        GlobalScope.launch { // ❌ memory leak
            delay(10000)
            updateUI() // might crash after Activity destroyed
        }
    }
}
🚫 GlobalScope runs for entire app lifetime. Never use it in Android. Replace with lifecycleScope or viewModelScope.
🧪 #16 Testing coroutines (runTest) Scenario: Unit test with virtual time 
@Test
fun testTimeout() = runTest {
    val result = withTimeoutOrNull(1000) {
        delay(2000)
        "done"
    }
    assertNull(result) // passes instantly, no real delay
}
⚙️ runTest automatically skips delays. You can also use advanceTimeBy() to test exact timing.
📦 #17 Mutex vs synchronized Scenario: Shared mutable state with coroutines 
val mutex = Mutex()
var counter = 0
repeat(10_000) {
    launch {
        mutex.withLock { counter++ } // safe concurrency
    }
}
🔒 Mutex is suspend-friendly alternative to synchronized blocks (which block threads). Avoid thread blocking inside coroutines.
🧩 #18 SharedFlow vs StateFlow — when to use each 
val state = MutableStateFlow(0)      // holds a single value (like LiveData)
val events = MutableSharedFlow<String>() // for one-time events (toasts, navigation)
StateFlow: always has a value, suitable for UI state. SharedFlow: hot stream, can emit multiple values without "state", perfect for event bus.
⏳ #19 Channel vs Flow Scenario: Producer-consumer communication 
val channel = Channel<Int>()
launch { repeat(5) { channel.send(it) }; channel.close() }
launch { for (x in channel) println(x) }
📡 Channel is hot, point-to-point communication. Flow is cold, reactive stream. Use Channels for coroutine coordination, Flow for declarative data pipelines.
🧹 #20 NonCancellable block for cleanup Scenario: Ensure cleanup even after cancellation 
launch {
    try {
        doWork()
    } finally {
        withContext(NonCancellable) {
            closeResources() // this block won't be cancelled
        }
    }
}
🧽 NonCancellable ensures cleanup code runs even if coroutine was cancelled. Essential for files, DB transactions, or network close.

🎯 Dispatcher Comparison — Advanced Insight

Dispatchers.Main
UI thread, bound to main looper. Never block
Dispatchers.IO
Flexible pool (up to 64). For blocking calls (network, disk).
Dispatchers.Default
CPU bound, limited to #cores. Parsing, sorting, bitmap.
Dispatchers.Unconfined
Starts in caller, may resume anywhere. Avoid, dangerous
🧠 Senior-level twist: "What happens if I call withContext(Dispatchers.IO) from Dispatchers.Main?" → It suspends the Main coroutine, moves work to IO pool, then resumes on Main — completely safe.

💬 Bonus: Advanced Follow-up Questions & Answers

❓ Q: How does delay differ from Thread.sleep?
✔ delay is a suspending function: does NOT block the thread; other coroutines run on same thread. Thread.sleep blocks the entire thread — never use in coroutines.
❓ Q: Can we cancel a coroutine that is inside a blocking call like InputStream.read()?
✔ Not automatically, because blocking code doesn’t respond to cancellation. Wrap it with withContext(Dispatchers.IO) + use suspendCancellableCoroutine or future.cancel() for true interrupt.
❓ Q: What is the difference between Job and SupervisorJob?
✔ In a Job, child failure cancels parent → all children cancelled. In SupervisorJob, child failure does NOT affect other children — used with supervisorScope.
❓ Q: How to retry a failed coroutine task?
✔ Use retry operator from Flow, or wrap in a while loop with delay & exception catch. For async, manually retry inside a suspend function.

🧪 Production-ready Pattern: Suspend function with timeout & fallback

suspend fun fetchDataWithFallback(): String = withTimeoutOrNull(2000) {
        fetchRemote()
    } ?: run {
        getCachedData() ?: "Default fallback"
    }
⏱️ Elegant timeout + fallback chain. Non-blocking + safe for production.
