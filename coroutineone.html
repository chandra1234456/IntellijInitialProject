📌 1. Core Demo: Parallel Fetch + Cancellation + Dispatcher Switching

import kotlinx.coroutines.*

suspend fun fetchUser(): String {
    delay(2000)           // simulates network
    return "👤 Alice"
}

suspend fun fetchPosts(): String {
    delay(3000)
    return "📝 3 posts"
}

fun main() = runBlocking {
    val parentJob = launch(Dispatchers.IO) {
        // 🧩 Parallel execution using async
        val userDeferred = async { fetchUser() }
        val postsDeferred = async { fetchPosts() }

        // Wait for both results
        val user = userDeferred.await()
        val posts = postsDeferred.await()

        // CPU processing
        withContext(Dispatchers.Default) {
            println("⚙️ Processing data on ${Thread.currentThread().name}")
        }

        // Back to UI (simulated)
        withContext(Dispatchers.Main) {
            println("✅ $user + $posts (UI update)")
        }
    }

    delay(2500)  // simulate user leaving after 2.5 sec
    parentJob.cancel()
    println("🛑 Parent coroutine cancelled — children stop automatically")
}
💡 Interview Tip: Explain that withContext(Dispatchers.Main) does NOT create a new coroutine — it just suspends & switches context. Perfect for thread hopping.

🧩 2. More Interview Scenarios (Senior-Level)

🔁 Scenario A: Sequential vs Parallel – Common Mistake

Wrong (sequential): val a = fetchA(); val b = fetchB() – slower because each suspends sequentially.
✔ Correct parallel: val a = async { fetchA() }; val b = async { fetchB() }; a.await() + b.await().

✅ Follow-up: "Coroutines with async allow structured parallelism without threads. Use it for independent tasks."
⚠️ Scenario B: Exception Propagation & supervisorScope

If one child fails in a regular scope, siblings + parent cancel. To avoid that → supervisorScope { ... } or SupervisorJob().

supervisorScope {
    launch { throw RuntimeException("Network fail") }   // crashes alone
    launch { delay(500); println("✅ I survive!") }     // still runs
}
🎙️ "supervisorScope allows independent task failure. Ideal for loading multiple features where one failure shouldn't break the whole screen."
⏱️ Scenario C: Cancellation resistance – Why coroutine keeps running?

If your coroutine has no suspension points (like a while(true) with CPU work), cancellation won't happen. Fix: use yield() or check isActive.

while (isActive) {
    // heavy computation
    yield() // or delay(1)
}
Cooperative cancellation Must check or suspend
📦 Scenario D: Memory Leak with GlobalScope (Anti-pattern)

GlobalScope.launch { ... } runs until app dies → leaks ViewModels/Activities. Always use lifecycle-aware scopes.

✔ Solution: viewModelScope in Android, custom CoroutineScope(Job() + Dispatchers.IO) and cancel manually.
⚡ Scenario E: Dispatcher Misuse – CPU work on Dispatchers.IO

Heavy JSON parsing or encryption on IO → reduces throughput because IO pool is not optimized for CPU crunch.
✔ Fix: withContext(Dispatchers.Default) { parseJson() }

🔄 5. Structured Concurrency & Parent-Child Relationship – Visual Explanation

scope.launch {          // parent coroutine
    launch { /* child 1 */ }
    async { /* child 2 */ }
}   // parent waits for children → cancellation propagates

✅ Structured concurrency ensures no coroutine is lost, and cancellation is automatic.
📌 Failure rule: By default failure of any child → cancels parent and all siblings. Use SupervisorJob or supervisorScope to isolate failures.

    assertEquals("User Data", result)
    // advanceTimeBy(2000) to control virtual time
}

📌 8. Cancellation Best Practices + Code Snippet

val job = scope.launch {
    repeat(1000) { i ->
        if (!isActive) return@launch   // cooperative exit
        // or use ensureActive()
        compute(i)
    }
}
job.cancelAndJoin()   // wait for cancellation to finish

📣 In interviews, mention that cancellation throws CancellationException only at suspension points. Use NonCancellable for cleanup tasks: withContext(NonCancellable) { closeResource() }.

🚦 9. Real Android Scenario: viewModelScope + Flow + repeatOnLifecycle

class MyViewModel : ViewModel() {
    val uiState: Flow<UiState> = repository.getDataFlow()
}

// In Fragment:
viewLifecycleOwner.lifecycleScope.launch {
    viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.uiState.collect { state -> render(state) }
    }
}

💡 Why repeatOnLifecycle? Prevents flow collection in background (STOPPED), saving resources and avoiding crashes.

🎯 One-Page Cheat Sheet – Nail the Interview

  • ✅ Suspending functions ≠ coroutines; they are building blocks.
  • ✅ withContext does NOT create a new coroutine, only changes dispatcher.
  • ✅ launch { } vs async { } – return vs result.
  • ✅ Cancellation is cooperative: use ensureActive() / isActive.
  • ✅ Structured concurrency = parent waits for children, cancel hierarchy.
  • ✅ supervisorScope = one failure does not cancel others.
  • ✅ Never use GlobalScope in Android apps → memory leaks.
  • ✅ Dispatchers.IO for blocking calls, Default for CPU crunch, Main for UI.

💬 Senior Follow-up Questions – Be Prepared

Q1: "Can withContext cause deadlock?"
Not typically, but if you call withContext(Dispatchers.Main) from Main thread inside a coroutine that's already on Main, it works fine (just suspends). However, if you call it from a non-suspend blocking code wrapped with runBlocking on Main → could cause UI freeze. Generally safe.
Q2: "Explain job.join() vs deferred.await()"
join() suspends until job completes (no result). await() suspends and returns the result or throws exception. Both respect structured concurrency.
Q3: "What is CoroutineStart parameter?"
launch(start = CoroutineStart.LAZY) starts coroutine only when needed (by start() or join()). Rare, but useful for lazy initialization.
Q4: "Difference between coroutineScope and supervisorScope?"
coroutineScope – fails fast if any child fails. supervisorScope – isolates failures, other children continue.

🏁 Final Code: Production-Ready Pattern for Android

class MainActivity : AppCompatActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        super.onCreate(savedInstanceState)
        lifecycleScope.launch {
            try {
                val data = withContext(Dispatchers.IO) { fetchRemoteData() }
                val processed = withContext(Dispatchers.Default) { processData(data) }
                withContext(Dispatchers.Main) { updateUI(processed) }
            } catch (e: CancellationException) {
                // coroutine cancelled — do nothing
            } catch (e: Exception) {
                showError(e.message)
            }
        }
    }
}
🎤 Interview Tip: Mention that lifecycleScope cancels automatically, and catching CancellationException is important to not swallow cancellation signals.
