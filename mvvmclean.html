MVVM & Clean Architecture Interview Questions & Answers

Basic (Fundamentals)

1. What is MVVM architecture?
MVVM separates app into Model (data), View (UI), and ViewModel (UI logic). It improves separation of concerns and testability.
2. Responsibilities of Model, View, ViewModel?
Model → data sources, View → UI rendering, ViewModel → holds UI state and business-related UI logic.
3. Why use ViewModel?
To survive configuration changes and keep UI data separate from Activity/Fragment lifecycle.
4. How ViewModel survives rotation?
It is stored in ViewModelStore which survives configuration changes unlike Activity.
5. LiveData / StateFlow?
Both are observable data holders. LiveData is lifecycle-aware; StateFlow is coroutine-based and more powerful.
6. LiveData vs StateFlow?
StateFlow is preferred in modern apps due to better performance, operators, and coroutine support.
7. Separation of concerns?
Splitting code into layers so each class has a single responsibility.

Intermediate

8. What is Clean Architecture?
A layered architecture that separates UI, business logic, and data layers for scalability and testability.
9. Layers in Clean Architecture?
Presentation (UI), Domain (UseCases), Data (Repository, API, DB).
10. Role of Domain layer?
Contains business logic and UseCases independent of Android framework.
11. What is UseCase?
A class that represents a single business operation like LoginUser or GetUserProfile.
12. Why not business logic in ViewModel?
It reduces testability and breaks separation of concerns. Business logic belongs in Domain layer.
13. Repository pattern?
Acts as a single source of truth between API, DB, and ViewModel.
14. Data flow in MVVM + Clean Architecture?
UI → ViewModel → UseCase → Repository → Data Source → back to UI.
15. Error handling in MVVM?
Use sealed classes (Loading, Success, Error) and propagate errors via StateFlow.

Advanced

16. Scalable Android app design?
Use Clean Architecture, modularization, Hilt DI, UseCases, and stateless UI.
17. Multiple data sources?
Repository decides source: API for fresh data, Room for cache.
18. Testing ViewModel/UseCase?
Mock repository using Mockito and test StateFlow outputs with JUnit.
19. DI in Clean Architecture?
Hilt provides dependencies like Repository and UseCases to ViewModel without manual creation.
20. State in Compose + MVVM?
ViewModel exposes StateFlow; Compose observes it using collectAsState().
21. Common MVVM mistakes?
Putting business logic in ViewModel, tight coupling, skipping UseCase layer.
22. Avoid tight coupling?
Use interfaces, repository abstraction, and dependency injection.
23. SOLID principles?
Design principles to make code scalable: Single Responsibility, Open/Closed, etc.

Scenario-Based

24. Design login feature?
UI → ViewModel → LoginUseCase → Repository → API. State handled using Loading/Success/Error.
25. Cache API using Room?
Fetch from API → store in Room → return Room as source of truth.
26. API fails but DB has data?
Return cached DB data and show error message or stale data indicator.
27. Project structure?
Feature-based modular structure with separate data, domain, and presentation packages.
28. Pagination?
Use Paging 3 library with Room + API integration.
29. UI state handling?
Use sealed class: Loading, Success, Error for predictable UI rendering.

Tricky Questions

30. Why ViewModel not in Domain?
Because ViewModel depends on Android framework; Domain must be pure Kotlin.
31. Can ViewModel call Retrofit?
No. It should go through UseCase and Repository.
32. Should Repository have business logic?
No. Repository handles data only, not business rules.
33. Skip UseCase layer?
Allowed in small apps, but reduces scalability and testability.
34. MVVM without Clean Architecture?
Possible, but harder to scale and maintain in large apps.
35. One-time events?
Use SharedFlow or Event wrapper to avoid re-triggering on rotation.
36. State vs Event?
State is persistent UI data; Event is one-time actions like navigation or toast.
