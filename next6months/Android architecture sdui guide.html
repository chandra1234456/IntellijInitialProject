01

Server-Driven UI (SDUI)

The server sends a description of the screen — not just data — and the client renders it. It's the architecture behind why Instagram, Airbnb, and DoorDash can change parts of their UI without an app release.

In a normal app, a screen's layout is compiled into the APK: if product wants to reorder a home-feed section, that's a code change, a review, a release, and a wait for Play Store rollout. SDUI moves that decision to the backend. The client ships a small set of generic, reusable components once — a card, a carousel, a banner — and the server sends JSON describing which components to show, in what order, and with what data. Change the JSON, and every installed app updates instantly, no release required.

WHERE IT'S USED IN THE WILD

Airbnb, Yelp, Nubank, DoorDash, and Lyft have all publicly discussed backend-driven UI systems for parts of their apps — usually growth surfaces, home feeds, and onboarding, not the whole app. Google's own AndroidX Remote Compose library (alpha, actively developed through 2026) is the clearest sign the idea is moving toward being a first-class Jetpack tool rather than a custom-built-per-company hack.

WHEN NOT TO REACH FOR IT

Performance-critical screens, OS-level integrations, offline-first flows, and anything needing pixel-perfect native feel usually stay fully native. Most real systems are hybrid: native shell + SDUI only where iteration speed matters (paywalls, promos, onboarding, A/B-tested surfaces).

Interview framing: "SDUI trades release-cycle speed for client complexity and a versioning/rollback problem" is a stronger answer than just describing what it is — interviewers are checking if you understand the trade-off, not just the buzzword.

02

App Architecture: Clean Architecture, MVVM, MVI

This is the single most-asked topic in mid-to-senior Android interviews. Know the layers, know why each exists, and be ready to draw it.

UI (Compose/View)
↕
ViewModel
↕
Domain (Use Cases)
↕
Data (Repository → Room / Retrofit)

Clean Architecture separates the app into UI, domain, and data layers so business logic doesn't depend on Android framework classes — the domain layer is plain Kotlin, testable without a device or emulator. MVVM is about how the UI layer itself is organized: the View observes a ViewModel's exposed state (StateFlow/LiveData) instead of pulling data imperatively. MVI goes further — a single immutable UI state, and every user action becomes an explicit "Intent" that produces a new state, which makes state changes traceable and testable in a way MVVM alone doesn't guarantee.

Interview framing: "MVVM vs MVI" isn't really a rivalry — most teams run MVVM at the framework level and adopt MVI's single-state-object discipline inside it. Saying that shows you've used both, not just read about them.

03

Design Patterns That Actually Come Up

Not the full Gang-of-Four catalogue — just the ones woven into the Android SDK and libraries you already use daily.

Repository structural
Single source of truth that hides whether data came from network, disk, or cache behind one API.
Where you've used it: every ViewModel that calls a Repository instead of Retrofit directly.
Observer behavioral
Subjects notify observers of state changes without knowing who's listening.
Where you've used it: LiveData, StateFlow/SharedFlow, RecyclerView's adapter notifyDataSetChanged.
Builder creational
Constructs complex objects step by step instead of one giant constructor.
Where you've used it: AlertDialog.Builder, Retrofit.Builder, NotificationCompat.Builder.
Singleton creational
One instance, globally accessible — powerful, but easy to abuse into hidden global state.
Where you've used it: Room database instance, Retrofit client, Hilt's @Singleton scope.
Factory creational
Delegates object creation to a method so callers don't need to know the concrete class.
Where you've used it: ViewModelProvider.Factory, LayoutInflater.
Adapter structural
Converts one interface into another the client expects, without changing either side.
Where you've used it: RecyclerView.Adapter — converting a data list into bindable view holders.
Strategy behavioral
Encapsulates interchangeable algorithms behind a common interface, swappable at runtime.
Where you've used it: RecyclerView.LayoutManager (Linear vs Grid vs Staggered — same interface, different layout strategy).
Dependency Injection architectural
Objects receive their dependencies instead of constructing them, decoupling and enabling testing.
Where you've used it: Hilt/Dagger, or manual constructor injection.
Facade structural
A simple front door over a complex subsystem.
Where you've used it: WorkManager hiding job scheduling across API levels; a Repository facading multiple data sources.

What Interviewers Actually Probe For

Beyond "explain MVVM" — the follow-up questions that separate a memorized answer from real experience.

  • Why does the domain layer avoid importing anything from android.* packages?
  • How would you test a ViewModel without touching Android framework classes?
  • Where does configuration change (screen rotation) fit into this architecture, and what breaks if you get it wrong?
  • If two API calls both write to the same Room table, how do you avoid a race condition?
  • What's the actual difference between StateFlow and SharedFlow, and when would each cause a bug if swapped?
  • In an SDUI system, how do you handle a client that doesn't yet support a component the server just started sending?
  • How do you version an SDUI schema without breaking users on an old app version?
  • Single-Activity vs multi-Activity — what's the actual architectural argument, not just "Google recommends it"?
