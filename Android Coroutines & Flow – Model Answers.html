Android Coroutines, Flow & Architecture – Model Answers

Section 1: Coroutines & API Calls

Q1. Parallel API calls?
Independent API calls should run in parallel using async.

coroutineScope {
  val user = async { getUser() }
  val orders = async { getOrders() }
  val notifications = async { getNotifications() }
}
Q2. Sequential execution?
Call APIs one after another when there is dependency.

val token = login()
val profile = fetchProfile(token)
Q3. Why withContext instead of launch?
withContext switches thread without creating a new coroutine. It preserves structured concurrency and allows returning a result.
Q4. What if one async fails?
In coroutineScope, if one async fails, all siblings are cancelled. This ensures consistency and avoids partial results.

Section 2: Dispatcher & Scope

Q5. API call in viewModelScope without dispatcher?
Runs on Dispatchers.Main. Risk: UI freeze / ANR.
Q6. When to use SupervisorJob?
When child coroutines should fail independently. Example: parallel analytics uploads.

Section 3: Flow, StateFlow, SharedFlow

Q7. Why StateFlow for UI?
StateFlow always holds the latest value and is lifecycle-friendly. UI can re-render safely after configuration changes.
Q8. Navigation event triggered twice?
Use SharedFlow because navigation is a one-time event, not UI state.
Q9. Cold vs Hot Flow?
Cold Flow starts when collected (Flow builder). Hot Flow emits regardless of collectors (StateFlow, SharedFlow).

Section 4: Database + Coroutines

Q10. Dispatcher for DB insert?
Dispatchers.IO because database operations are blocking I/O tasks.
Q11. Expose Room DB to UI?
Use Room DAO returning Flow.

@Query("SELECT * FROM events")
fun getEvents(): Flow<List<Event>>

Section 5: Analytics Scenario

Q12. Offline analytics design?
Save events in Room DB using IO dispatcher. Sync events using WorkManager + coroutines when network is available.
Q13. Why IO dispatcher for analytics?
Analytics involves disk writes and network calls which are blocking operations.

Section 6: Lifecycle & Cancellation

Q14. API continues after Activity destroyed?
Used wrong scope (GlobalScope or custom scope). Fix: use lifecycleScope or viewModelScope.
Q15. Why repeatOnLifecycle?
It automatically starts and stops Flow collection based on lifecycle state, preventing memory leaks.

Section 7: Debugging & Tricky

Q16. Job cancelled but still running?
Blocking code like Thread.sleep() or no suspension points. Coroutines are cooperative.
Q17. Cancellation vs Exception?
Cancellation is normal lifecycle behavior. Exceptions indicate failure and cancel parent coroutines.

Final Round

Q18. End-to-end flow explanation?
UI triggers ViewModel → API call on IO → save to DB → DB exposes Flow → UI collects StateFlow.
Q19. Common ANR mistakes?
Network on Main thread, heavy work on IO instead of Default, using runBlocking on UI thread.
Q20. Explain coroutines to junior?
Coroutines allow writing async code like normal code, without blocking threads, safely tied to lifecycle.
