Interview Questions & Answers

Architecture Question

1. Design an Android app using MVVM + Clean Architecture. Explain the complete data flow from UI to data source and back.

In an Android app using MVVM + Clean Architecture, the system is divided into clearly separated layers to ensure scalability, testability, and maintainability.

1. Presentation Layer (UI + ViewModel)

  • UI (Jetpack Compose / Activity / Fragment) only displays state.
  • Observes state from ViewModel using StateFlow / LiveData.
  • ViewModel holds UI state and handles user events.
  • It does NOT access API or database directly.
  • Calls UseCases from the domain layer.

2. Domain Layer (Use Cases)

  • Contains business logic of the application.
  • Each UseCase represents a single responsibility (e.g., GetUserProfile, LoginUser).
  • Acts as a bridge between ViewModel and Repository.
  • Independent of Android framework.

3. Data Layer (Repository)

  • Handles data operations from remote and local sources.
  • Fetches data from API (Retrofit) or local DB (Room).
  • Provides a single source of truth to the domain layer.

Complete Data Flow

  • User interacts with UI (button click / screen load)
  • UI sends event to ViewModel
  • ViewModel calls a UseCase
  • UseCase executes business logic
  • UseCase calls Repository
  • Repository fetches data (API / DB / cache)
  • Data flows back through UseCase → ViewModel
  • ViewModel updates UI state (Loading → Success → Error)
  • UI re-renders automatically via Compose
2. If API fails but Room has data, what will you show in UI and how will you design the flow in MVVM + Clean Architecture?

✔ Data Flow (MVVM + Clean Architecture)

  • UI requests data via ViewModel
  • ViewModel calls UseCase
  • UseCase delegates to Repository
  • Repository tries API call first

✔ Repository Decision Logic

  • If API succeeds:
    • Save response into Room DB
    • Return fresh data to domain layer
  • If API fails:
    • Fetch cached data from Room DB
    • Return cached data to UI

✔ UI Behavior

  • Loading → while fetching data
  • Success → show fresh API data
  • Offline fallback → show cached Room data with optional message
  • Error → if both API and cache fail

⭐ Key Concept

Room acts as a cache layer or sometimes a single source of truth, depending on whether the app follows an offline-first or network-first strategy.

🔥 Final Interview Answer

“Repository first tries the API, saves the response into Room if successful, and if the API fails, it returns cached Room data so the UI can still display content.”

3. If both API fails AND Room is empty, what should UI do and how will you handle it in architecture?

✔ Scenario Handling

  • API fails (network error, timeout, etc.)
  • Room DB is also empty

✔ Proper Strategy

1. Limited Retry (Optional)

  • Retry API call 2–3 times only
  • Use exponential backoff
  • Avoid infinite retries (battery + performance concern)

2. If Still Fails

  • Stop automatic retry
  • Move to error handling state

✔ UI State Handling

  • Loading → fetching data
  • Error → API + DB both failed
  • Empty State → no cached data available

✔ UI Should Show

  • "No data available"
  • "Check your internet connection"
  • Retry button for manual action

🔥 Final Interview Answer

“If both API and Room fail, we retry API a limited number of times using exponential backoff. If it still fails, we stop automatic retries and show an empty/error state in the UI with a manual retry option.”

4. Where should retry logic live—in ViewModel, Repository, or UseCase? And why?

✔ 1. Repository Layer (Automatic Retry)

  • Handles transient failures (network timeout, temporary issues)
  • Implements limited retries (2–3 attempts)
  • Uses exponential backoff strategy

Reason: Repository is responsible for data reliability and source handling.

✔ 2. ViewModel Layer (UI State)

  • Does NOT handle retry logic itself
  • Exposes state (Loading / Success / Error)
  • Triggers UseCase calls

✔ 3. UI Layer (User Retry)

  • User clicks retry button
  • Flow restarts: UI → ViewModel → UseCase → Repository
  • This is a fresh request, not internal retry logic

✔ Why this separation?

  • Avoid infinite retry loops
  • Prevent UI blocking
  • Avoid unnecessary network load
  • Clear separation of concerns

🔥 Final Interview Answer

“Automatic retry logic for network failures belongs to the Repository layer with limited attempts and exponential backoff. If it still fails, we expose an error state to the ViewModel, and the user can manually retry via the UI, which triggers a fresh request flow.”

5. Why do we need UseCase layer in Clean Architecture?

✔ Purpose of UseCase

  • Encapsulates a single business operation
  • Keeps ViewModel clean and UI-focused
  • Acts as a bridge between ViewModel and Repository
  • Improves reusability of business logic
  • Makes business rules independently testable

✔ Problem it solves

  • Prevents ViewModel from becoming bloated
  • Avoids duplication of business logic across screens
  • Decouples UI layer from data layer

✔ Dependency Rule (Important)

In Clean Architecture, ViewModel depends on UseCase, not Repository directly. This maintains proper layer separation and avoids tight coupling.

🔥 Final Interview Answer

“UseCase is used to separate business logic from the ViewModel, ensuring Single Responsibility Principle. It keeps ViewModel focused on UI state, improves testability, and provides a clean boundary between UI and data layers.”

6. Can ViewModel call Repository directly? If yes, why do we still use UseCase?

✔ Short Answer

Yes, in basic MVVM architecture ViewModel can directly call Repository. But in Clean Architecture, we avoid that.

✔ Why UseCase is introduced

  • Enforces separation of concerns
  • Keeps business logic out of ViewModel
  • Improves scalability for large apps
  • Ensures consistent architecture boundaries

✔ Dependency Flow

ViewModel → UseCase → Repository → Data Sources

🔥 Final Interview Answer

“Yes, ViewModel can directly call Repository in simple MVVM. However, in Clean Architecture we introduce UseCase to separate business logic from the UI layer, enforce architecture boundaries, improve testability, and ensure ViewModel depends on UseCase instead of Repository.”

7. If UseCase only calls Repository, is it still useful?

✔ Yes — and here’s why

1. Future-proofing

  • Today it may just call Repository
  • Tomorrow it may include validation, mapping, or business rules

2. Clear architecture boundary

  • ViewModel = UI logic only
  • UseCase = business layer
  • Repository = data layer

3. Reusability

  • Same UseCase can be used across multiple ViewModels
  • Prevents logic duplication

4. Testability

  • UseCase can be tested in isolation
  • No dependency on UI or Android framework

🔥 Final Interview Answer

“Yes, even if a UseCase only calls a Repository, it is still useful because it acts as a clean boundary for business logic. It enables future scalability, improves testability, enforces separation of concerns, and allows reuse across multiple ViewModels without duplication.”

8. What is the difference between State and Event in MVVM (especially in Jetpack Compose)?

✔ What is State?

  • Represents UI data at a given point in time
  • Can be observed and re-rendered on recomposition
  • Persistent and survives configuration changes (when properly scoped)

Examples: Loading, Success, Error, list data, form inputs

✔ What is Event?

  • Represents a one-time action
  • Should be consumed only once
  • Should NOT be re-triggered on recomposition

Examples: Navigation, Toast, showing dialog, API trigger

✔ Key Difference

  • State: persistent UI data (UI reflects it continuously)
  • Event: one-time action (consumed once)

🔥 Final Interview Answer

“State represents persistent UI data like loading, success, or error and is continuously observed by the UI. Event represents one-time actions like navigation or toast messages that should be consumed only once and not re-triggered on recomposition.”

9. Why do we use StateFlow instead of LiveData in modern Android apps?

✔ Key Difference

  • LiveData: lifecycle-aware by default
  • StateFlow: coroutine-based state holder (not lifecycle-aware by default)

✔ Why StateFlow is preferred

  • Native support for Kotlin Coroutines
  • Supports operators (map, combine, filter)
  • Better integration with Jetpack Compose
  • Always holds the latest state
  • More predictable state management

✔ LiveData limitations

  • Limited functional operators
  • Not coroutine-friendly
  • Less flexible for complex transformations

✔ Important Interview Point

StateFlow becomes lifecycle-safe when collected properly using lifecycle-aware collectors like repeatOnLifecycle or collectAsStateWithLifecycle.

🔥 Final Interview Answer

“StateFlow is preferred over LiveData because it integrates natively with Kotlin Coroutines, supports advanced operators, and works better with Jetpack Compose. Although LiveData is lifecycle-aware by default, StateFlow provides more flexibility and control when used with proper lifecycle handling.”

10. If StateFlow is not lifecycle-aware, how do you safely collect it in Activity or Compose?

✔ Problem

  • StateFlow can continue emitting even when UI is inactive
  • This may cause memory leaks or unnecessary updates

✔ Solution

In Jetpack Compose

  • Use collectAsStateWithLifecycle()

In Activity / Fragment

  • Use repeatOnLifecycle(Lifecycle.State.STARTED)

✔ Why this works

  • Stops collection when UI is in background
  • Prevents memory leaks
  • Saves CPU and battery

🔥 Final Interview Answer

“Since StateFlow is not lifecycle-aware by default, we make it safe by collecting it using lifecycle-aware scopes. In Compose we use collectAsStateWithLifecycle, and in Activities or Fragments we use repeatOnLifecycle to ensure updates happen only when the UI is active.”

11. What is Single Source of Truth (SSOT) in MVVM + Clean Architecture?

✔ Definition

Single Source of Truth (SSOT) means the app has only one trusted data source for a given piece of information.

✔ In Clean Architecture

  • Repository or Room DB acts as SSOT
  • UI observes only one source
  • Prevents inconsistent data between API and cache

✔ Recommended Flow

  • API fetches data
  • Repository stores it in Room DB
  • UI observes Room DB
  • Any update reflects automatically in UI

🔥 Final Interview Answer

“Single Source of Truth means maintaining one consistent and trusted data source for the UI. In Clean Architecture, Room database or Repository acts as SSOT so the UI always observes consistent data instead of directly depending on multiple sources like API and DB.”

12. What is the difference between Repository and UseCase?

✔ Repository (Data Layer)

  • Handles data sources (API, DB, cache)
  • Decides where data comes from
  • No business logic

✔ UseCase (Domain Layer)

  • Contains business logic
  • Represents a single action (LoginUser, GetUser)
  • Uses Repository to get data

✔ Simple Analogy

  • Repository = Supplier (provides raw data)
  • UseCase = Chef (processes and applies logic)

✔ Key Difference

  • Repository → data-focused
  • UseCase → logic-focused

🔥 Final Interview Answer

“Repository handles data operations from API and database, while UseCase contains business logic and defines specific actions. Repository is data-focused, whereas UseCase is logic-focused and sits between ViewModel and Repository in Clean Architecture.”
