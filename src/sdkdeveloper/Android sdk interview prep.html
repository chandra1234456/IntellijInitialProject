Most Frequently Asked SDK Questions

What is an Android SDK?

A packaged set of tools, libraries, and APIs that lets another app integrate specific functionality without rebuilding it from scratch — distributed to consumers rather than run as a standalone app.

What is an AAR file, and how is it different from an APK?

An AAR is a compiled Android library archive — code, resources, and manifest — meant to be consumed by another project. An APK is a runnable, installable app package. AARs can't run on a device on their own.

What's the difference between api and implementation in Gradle?

implementation hides a dependency from consumers of your module (faster builds, smaller public surface); api exposes it transitively. SDKs should default to implementation unless a type genuinely needs to be exposed.

How do you design a reusable SDK?

Keep the public surface small and intentional, hide internals behind internal/private visibility, avoid leaking third-party types in your API, and design for the integrator's mental model rather than your own implementation.

How do you avoid memory leaks in an SDK?

Never hold static references to Context or Activity, unregister listeners/receivers in the correct lifecycle callback, scope coroutines properly, and verify with LeakCanary during development.

What is backward compatibility, and how do you preserve it?

Ensuring older integrations keep working after an SDK update. Preserve it with semantic versioning, deprecation windows instead of hard removals, and treating any public signature change as a breaking change.

How do you version and publish an SDK?

Semantic versioning (major.minor.patch), publish via Maven Central, JitPack, or an internal Artifactory/Nexus repo using the maven-publish Gradle plugin, with signed artifacts and clear release notes.

How do you secure an SDK?

SSL pinning for network calls, Android Keystore / EncryptedSharedPreferences for secrets, no hardcoded API keys, and ProGuard/R8 keep rules that protect internals without breaking consumers.

How do you prevent the SDK from crashing the host application?

Wrap every public entry point in defensive try/catch, return typed results or sealed error states instead of throwing, and never let an internal exception propagate uncaught across the SDK boundary.

How do you expose your SDK to Flutter?

Via a Flutter plugin using MethodChannel (and EventChannel for streams), serializing data to primitives/maps, and marshaling callbacks back onto the correct thread.

How do you reduce SDK size?

Enable R8/ProGuard shrinking, avoid heavy transitive dependencies, split optional features into separate artifacts, and audit resources that get bundled unnecessarily.

How do you test an SDK?

Unit tests (JUnit + MockK/Mockito) for logic, Turbine for Flow emissions, instrumented/Espresso tests sparingly for UI components, and a sample host app to validate real integration behavior.

Best Way to Stand Out

Build a small sample SDK — a logging, authentication, or analytics module — and take it all the way through the pipeline a real SDK would go through:

  • Package it as an AAR and publish it to a local Maven repository
  • Integrate it into a native Android app
  • Integrate it into a Flutter app via MethodChannel
  • Integrate it into a React Native app via a Native Module

Being able to demo a working SDK — even a small one — during the interview carries more weight than reciting concepts alone.
