SOLID Principles in Android Kotlin

1. Single Responsibility Principle (SRP)

A class should have only one responsibility.

❌ Bad Example

class UserManager {

    fun saveUser(user: User) {
        // Save to database
    }

    fun validateUser(user: User): Boolean {
        return user.name.isNotEmpty()
    }

    fun sendEmail(user: User) {
        // Send email
    }
}

✅ Good Example

class UserValidator {
    fun validate(user: User): Boolean {
        return user.name.isNotEmpty()
    }
}

class UserRepository {
    fun save(user: User) {
        // Save user
    }
}

class EmailService {
    fun send(user: User) {
        // Send email
    }
}

2. Open/Closed Principle (OCP)

Open for extension, closed for modification.

❌ Bad Example

class DiscountCalculator {

    fun calculate(type: String): Double {
        return when(type) {
            "Regular" -> 10.0
            "Premium" -> 20.0
            else -> 0.0
        }
    }
}

✅ Good Example

interface Discount {
    fun calculate(): Double
}

class RegularDiscount : Discount {
    override fun calculate() = 10.0
}

class PremiumDiscount : Discount {
    override fun calculate() = 20.0
}

3. Liskov Substitution Principle (LSP)

Subclasses should replace parent classes without breaking behavior.

❌ Bad Example

open class Bird {
    open fun fly() {}
}

class Penguin : Bird() {
    override fun fly() {
        throw Exception("Penguins can't fly")
    }
}

✅ Good Example

interface Bird

interface FlyingBird {
    fun fly()
}

class Sparrow : Bird, FlyingBird {
    override fun fly() {
        println("Flying")
    }
}

class Penguin : Bird

4. Interface Segregation Principle (ISP)

Clients should not depend on methods they don't use.

❌ Bad Example

interface Worker {
    fun work()
    fun eat()
}

class Robot : Worker {
    override fun work() {}

    override fun eat() {
        // Robots don't eat
    }
}

✅ Good Example

interface Workable {
    fun work()
}

interface Eatable {
    fun eat()
}

class Human : Workable, Eatable {

    override fun work() {}

    override fun eat() {}
}

class Robot : Workable {

    override fun work() {}
}

5. Dependency Inversion Principle (DIP)

Depend on abstractions, not concrete implementations.

❌ Bad Example

class UserViewModel {

    private val repository = UserRepository()

    fun loadUsers() {
        repository.getUsers()
    }
}

✅ Good Example

interface UserRepository {
    fun getUsers()
}

class UserRepositoryImpl : UserRepository {

    override fun getUsers() {
        // API call
    }
}

class UserViewModel(
    private val repository: UserRepository
) {

    fun loadUsers() {
        repository.getUsers()
    }
}

Dependency Injection with Hilt

@Module
@InstallIn(SingletonComponent::class)
object AppModule {

    @Provides
    fun provideRepository(): UserRepository {
        return UserRepositoryImpl()
    }
}

📌 SOLID Summary

  • S → Single Responsibility Principle
  • O → Open/Closed Principle
  • L → Liskov Substitution Principle
  • I → Interface Segregation Principle
  • D → Dependency Inversion Principle

Benefits in Android Development

  • ✅ Cleaner Architecture
  • ✅ Easier Unit Testing
  • ✅ Better Scalability
  • ✅ Reusable Components
  • ✅ Maintainable Codebase
